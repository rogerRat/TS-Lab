## 1. 实验目标（需要回答的三个问题）

1. **cu 与 ot 相对 rand 是否在多数任务上存在可观测优势？**
2. **cu 与 ot 二者谁更好？**
3. **支持集（candidate support）宽度是否影响表现？是否存在可观测的结论（如单调性/倒U形）？**

## 2. 实验矩阵

| 维度 | 取值 |
|---|---|
| seeds | 0, 1, 2, 3（共 4 个） |
| 任务 | FEV 20 任务中的 18 个（task-00…task-17；task-18/19 结构性跳过，见 §6.3） |
| 方法 | rand（random 基线）、cu（每个 reference segment 取 Top-K source 并集，候选集内均匀采样）、ot（静态 OT 主方法） |
| 总计 | 4 × 18 × 3 = 216 组训练+评估（task-18/19 结构性跳过） |

**方法语义**（全部为静态方法；CU 与 OT 完全独立）：
- cu：policy=candidate-uniform，对每个 reference segment 直接检索 neighbor_count 个 source 最近邻，所有 source ID 取并集，候选集内等质量 1/|support|；不调用 OT、不使用 reference 距离过滤。
- ot：policy=ot，使用完整静态 OT transport mass；neighbor_count 仅限制 OT 的候选池。

## 3. 关键参数（全部方法统一）

| 参数 | 值 |
|---|---|
| 模型 | Chronos（T5-efficient-tiny 架构，~9.4M），`initialization_mode: from_scratch`（全部随机初始化，`initializer_factor: 1.0`，词表 4096） |
| 训练步数 | 10000 |
| checkpoint | `[10000]`（**不保存任何中间 checkpoint**） |
| batch_size | 64 |
| 上下文 | context 512 / prediction 64，window_stride 1，missing_value_policy reject |
| 优化器 | AdamW lr=1e-3，linear scheduler（warmup 0），max_grad_norm 1.0，float32 + tf32 + torch_compile |
| 采样 OT | pot_sinkhorn_unbalanced，squared_euclidean，epsilon 0.1，mass_regularization 1.0，neighbor_count 256，support_threshold 0.5，λ=1.0 |
| 段设置 | **512+512（segment_length 512, stride 512）静态段**，复用现有 catalog：src/ref 均为 `1b-fev-segl512s512-dtrans-v2-20260817`（复用现有资源，不重建） |
| 评估 | FEV 单任务评估，bfloat16，batch 128，num_samples 20，temperature 1.0，top_k 50，eval seed 20260722；指标 SQL(主)/WQL/MASE/WAPE/MAE/MSE |
| reference | 每任务自引用（train_task_indices = eval_task_indices = [t]），reference_task_record = {benchmark: fev, task_indices: [t]} |

## 4. 资源与调度（压榨算力）

- 硬件：2 × RTX 5090（32GB each），208 核 CPU。
- **并行度：4 个 lane（每卡 2 进程）**，lane↔GPU 绑定：lane0,lane1→GPU0；lane2,lane3→GPU1（`CUDA_VISIBLE_DEVICES`）。
- **seed 串行**：按 seed 0→1→2→3 顺序完整跑完（每个 seed 内 20 个任务在 4 个 lane 上并行，每 lane 串行处理分到的任务队列），保证用户尽早看到 seed 0 的完整结果。
- **每个独立进程一个 tmux 终端**（计算资源节省机制的载体）：
  - `sr20-master`：总控进程（推进 seed、健康检查、汇总）；
  - `sr20-l0` … `sr20-l3`：4 个 lane 进程（seed 间复用同一会话名，由 master 重新投放命令）；
  - `sr20-watchdog`：看门狗（运行 `scripts/dock_shut.sh`，见下）。
  - 所有进程输出直接打在自己的 tmux pane 上（禁止重定向到文件导致 pane 静默）。
- 每个 (seed, task) 内部 3 个方法串行，顺序：rand → cu → ot。
- 断点续跑：完成证据为该方法 eval/<method>/10K/summary.csv 存在；不再使用 ratio 方法的 skip marker。
## 5. 磁盘安全（容器外存保护，硬性要求）

1. **禁止上传**（`upload_trained_models: false`，不调用 hub.ms）。
2. **模型文件即评即删**：每个方法的评估成功完成后，立即删除该方法的整个 `checkpoints/` 目录（含 checkpoint-step-010000、checkpoint-final、ts3_training_state.pt）。
3. **审计日志即评即删**：评估成功后同时删除该方法的 `training_audit/` 目录（实测每组约 400MB，560 组约 87GB，是磁盘最大威胁）。严格保留的轻量文本仅：`losses.csv`、`run_manifest.json`、`final_report.json`、`losses_by_step.png`。
4. **严格保留实验结果**：`eval/**`（summary.csv、fev_results.csv、task_*.json、fev_metadata.json）与 `vis/**` 绘图产物永不删除。"我只要实验结果"。
5. **缓存即用即删**：transfer cache 与训练 seed 无关（signature 不含 seed），4 个 seed 共享同一份 cache（布局见 §8）。每个任务该 seed 的全部方法完成后**立即删除该任务的所有 sr20-* cache**（20260820 变更：不再保留到最后一个 seed；因 task-18/19 事件后按"当轮用完即删"执行，后续 seed 需要时重建，构建仅约 1-3 分钟/个，可接受）。master 健康循环每 5 分钟兜底清扫：已完成评估的 audit、无 summary 残留 checkpoints、孤儿 cache。
6. 监控器每轮检查磁盘余量，低于 20GB 时在 ALERTS 中提醒（惰性提醒，见 §9）；master 与 lane 双侧执行删除逻辑（脚本内置，非人工）。

## 6. cu 附加记录与跳过规则

1. CU 审计字段：cache manifest 的 reference_diagnostics 记录 candidate_top_k、candidate_support_count、source_segment_count 及候选覆盖比例。
2. CU 语义约束：候选支持必须来自逐 reference-segment Top-K union，质量必须在候选支持上均匀；不得出现 OT transform、support ratio 或 top-mass 截断。
3. 任务级跳过：task-18 与 task-19 在窗口规格下无合法参考轨迹，整个任务跳过。

## 7. 触发式绘图（评估完成即绘）

- 每个方法**每次评估成功后立即**在该 (seed, task) 命名空间的 vis 目录执行绘图（同步触发，不是实验末尾统一绘）：
  1. **表现图**：`visualize.perf_step_line`（performance_by_step.csv + performance_steps.html/.png）——只要存在任一已完成评估结果就绘。
  2. **相对表现图**：`--relative-to-rand`（relative_to_rand_by_step.csv + relative_to_rand_steps.html/.png）——仅当 `rand` 与至少一个其他方法的结果都存在时触发。
- 绘图目录固定为该 (seed, task) 的 `vis/performance-steps/`（两张图同目录）。
- 绘图失败不阻塞主流程（记录告警，惰性提醒）。

## 8. 目录与命名布局（关键：cache 跨 seed 共享的实现）

```
configs/experiments/9m-sr20/
  reference-catalogs-XX/                 # 每 task 一个共享 symlink 视图（seed 无关，保证 cache signature 一致）
  s<seed>/sr20-task-XX/<method>.train.yaml / <method>.eval.yaml
outputs/run-9m-sr20/
  s<seed>/sr20-task-XX/
    train/<method>/{run_manifest.json, losses.csv, checkpoints/(临时,即评即删), SKIPPED-FULL-POPULATION?}
    eval/<method>/10K/{summary.csv, fev_results.csv, task_*.json, fev_metadata.json}
    vis/performance-steps/{performance_by_step.csv, performance_steps.html/.png,
                           relative_to_rand_by_step.csv, relative_to_rand_steps.html/.png}
outputs/cache/
  sr20-task-XX-<method>/<policy>/{manifest.json, sampling.safetensors}   # 4 seed 共享，末 seed 后删
logs/exp-sr20/                            # 驱动器与监控日志、milestones、ALERTS
```

- cache run_id 由训练进程从输出路径推导（`<output.parent.parent.name>-<method>`）；上述布局使 `output.parent.parent.name = sr20-task-XX`，与 seed 无关 → 4 个 seed 天然命中同一 cache（manifest run_id 与 signature 均一致，无需改核心代码）。
- 驱动脚本：`scripts/temp/exp_sr20.py`（生成配置 → 4 lane 调度 → cache/训练/评估/删模型/绘图 → 末 seed 删 cache → 汇总报告）。

## 9. 运行、看门狗与心跳

- 全程运行在 **tmux** 内（`sr20-*` 会话族），SSH 断连不影响。

### 9.1 看门狗（容器自动关停，节省算力）

- `sr20-watchdog` 会话运行 `scripts/dock_shut.sh --mode log --timeout 300 --sessions sr20-master sr20-l0 sr20-l1 sr20-l2 sr20-l3`。
- 逻辑（每会话独立倒计时）：
  1. 每个被监控会话有**自己**的 5 分钟（300s）倒计时；
  2. 该会话 pane 一旦出现**任何新日志输出**，仅重置**它自己**的倒计时；
  3. 会话从未出现过（尚未创建）不参与判定；会话已消失（曾存在）视为倒计时已结束；
  4. **只有当所有被监控会话的倒计时都已结束**，才执行 `/usr/bin/shutdown` 关闭整个容器。

### 9.2 心跳（看门狗机制的核心保障，硬性要求）

- **每一个长运行进程必须有自己的心跳日志**：lane 进程与 master 进程内置心跳线程，**每 60s** 向自己的 tmux pane 打印一行 `HEARTBEAT ...`（含当前 seed/task/method/phase/elapsed）。
- 原因：训练（10k 步）、评估（多窗口多目标）、cache 构建（源总体 4.88M 段的 OT）都可能出现远超 5 分钟的静默计算段；若无心跳，倒计时误触发会把整个容器关掉，造成实验中断。
- 训练子进程本身每 100 步记日志（`logging_interval_steps: 100`）；评估与 cache 构建的静默由 lane 心跳兜底。心跳间隔 60s << 300s 倒计时，留足裕量。
- 任何新增后台进程（如手动补跑）必须同样有 ≤60s 心跳，或加入 watchdog 监控前先确认其输出频率。

### 9.3 惰性提醒（不打屏）

- 只在以下事件写 `logs/exp-sr20/milestones.log` 与 `ALERTS.md`：
  - 每个 (seed, task) 完成或失败（含失败原因首行）；
  - seed 阶段切换；
  - 进程崩溃/lane 超过 30 分钟无新日志；
  - 磁盘余量 < 20GB；GPU 显存 > 30GB 或利用率长期为 0。
- master 每 5 分钟做一次健康检查，仅追加增量告警（同一告警不重复提醒）。
- 汇总交付：实验结束后生成 outputs/run-9m-sr20/SUMMARY.md（每 task×seed×方法的 SQL/WQL/MASE、相对 rand 变化、cu-vs-ot 胜负及候选支持覆盖率）。
